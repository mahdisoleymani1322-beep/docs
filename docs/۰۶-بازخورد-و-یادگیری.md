# ۰۶ — بازخورد و یادگیری

بازخورد سه لایه دارد. هر سه به یک مسیر داده می‌رسند: فایل‌های گیت‌شده که کد می‌خواند.

| لایه | از کی | به کجا | اثر |
|---|---|---|---|
| ۱. خودکار | داورها و چک‌ها | `issues.v<n>.json` ← writer | دور بعد Loop همین اجرا |
| ۲. انسانی | بازبین | `feedback/<run_id>.jsonl` | چرخه‌ی عمر سند؛ «درخواست تغییر» ← اجرای تازه |
| ۳. یادگیری | critic + انسان | `lessons/lessons.json`، گلدن‌ست | اجراهای بعدی همه‌ی سندها |

## ۱. بازخورد انسانی

اسکیل `/give-feedback` یا مستقیم `feedback.py add`. هر رکورد یک خط JSON در `feedback/<run_id>.jsonl` است:

| فیلد | مقدار |
|---|---|
| `ts` | زمان ثبت (ISO) |
| `run_id`، `version` | کدام سند و کدام نسخه |
| `section` | شناسه‌ی بخش (`S06`) یا `null` برای کل سند |
| `vote` | `up`، `down` یا `null` |
| `note` | توضیح آزاد |
| `action` | `review`، `request_changes`، `approve`، `decline` یا `null` |
| `author` | نام بازبین |
| `override_reason` | فقط برای تأیید سندی که `ready_for_review` نیست؛ اجباری در همان حالت |

### انتقال‌های مجاز `lifecycle`

| از | کنش | به | شرط |
|---|---|---|---|
| `draft` | `review` یا هر رأی و یادداشت | `in_review` | — |
| `draft` یا `in_review` | `request_changes` | `changes_requested` | حداقل یک یادداشت |
| `draft` یا `in_review` | `approve` | `approved` | `status = ready_for_review`، یا `override_reason` |
| `draft` یا `in_review` | `decline` | `declined` | — |
| `approved`، `declined`، `changes_requested` | هر کنش | — | رد می‌شود؛ وضعیت پایانی است |

`feedback.py` هر انتقال غیرمجاز را رد می‌کند و هیچ فایلی را تغییر نمی‌دهد.

### «درخواست تغییر» ← نسخه‌ی تازه (الگوی arkan-crm)

1. `feedback.py` یک اجرای تازه می‌سازد: همان `input.json`، `revision = قبلی + 1`، `parent_run = <run_id قبلی>`.
2. یادداشت‌های انسان به‌صورت ایرادهای `issues.v0.json` با منبع `human` به اجرای تازه می‌روند. نویسنده در دور ۱
   باید تک‌تک آن‌ها را در `revision.v1.json` پاسخ دهد: رفع‌شده یا رفع‌نشده با دلیل.
3. اجرای قبلی دست‌نخورده می‌ماند تا تاریخچه قابل مقایسه باشد.

## ۲. درس‌ها (حلقه‌ی یادگیری، الگوی arkan)

```
critic ← lessons.proposed.json ← lessons.py add (کد) ← lessons/lessons.json ← lessons.py inject ← context/lessons.<agent>.md
```

| قاعده | مقدار | اعمال با |
|---|---|---|
| درس تازه در هر اجرا | حداکثر ۳ | `lessons.py add` |
| درس فعال برای هر ایجنت | حداکثر ۸؛ قدیمی‌ترین بازنشسته می‌شود | `lessons.py add` |
| درس در پرامپت هر ایجنت | حداکثر ۵، جدیدترین‌ها | `lessons.py inject` |
| هر درس | خطاب به یک ایجنت موجود، حداکثر ۲۰۰ نویسه، قابل‌اجرا | schema `lesson` |
| حذف درس اشتباه | فقط انسان | `lessons.py retire L-..` |

**درس خوب** (نمونه از arkan): «writer: در مقدمه به‌جای کلی‌گویی، با یک مسئله‌ی ملموس مخاطب شروع کن.»
**درس بد:** «سند خوب بود.» (نه قابل‌اجرا است، نه عمومی)

منبع درس‌ها:
- **گزارش Loop:** ردیف‌هایی که مدام پایین ماندند، ایرادهایی که تکرار شدند.
- **بازخورد انسانی:** رأی منفی و یادداشت. رأی مثبت بدون یادداشت درسی ندارد.

اگر اجرا عالی بوده، critic عمداً درس کمتری می‌دهد، چون «درس بی‌ارزش خودش هزینه است و پرامپت‌ها را متورم می‌کند» (arkan).
شکست critic اجرای موفق را خراب نمی‌کند: درس‌گرفتن «تلاش حداکثری» است، نه بخشی از تولید سند.

## ۳. برچسب انسانی ← گلدن‌ست

وقتی بازبین با تصمیم دروازه مخالف است (مثلاً سندی را تأیید می‌کند که دروازه رد کرده بود، یا برعکس)، آن سند
نامزد گلدن‌ست است. افزودن به گلدن‌ست فقط با PR انسانی است ([`۰۳`](۰۳-سیستم-ارزیابی.md) بخش ۵). بعد از
افزودن، `kappa.py` دوباره اجرا می‌شود.

## ۴. داشبورد ایستا

`report.py` از `runs/`، `feedback/` و `lessons/` یک صفحه‌ی HTML می‌سازد:

- فهرست اجراها با وضعیت و `lifecycle`
- نمره‌ی هر دور و روند
- پرتکرارترین ایرادها
- رأی‌های انسانی
- درس‌های فعال

بدون سرور و بدون دیتابیس ([`۰۰`](۰۰-چشم‌انداز.md)، غیرهدف‌ها).
